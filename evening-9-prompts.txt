P1 [CRITICAL] — find_orphans / get_pair are non-recursive
-----------------------------------------------------------------------------

Repo: triage-keepers (Python, MCP server)
File: server.py
Functions: find_orphans (line 449), get_pair (line 400)

Problem:
Both functions call folder_path.iterdir(), which only lists direct children.
When the user passes a folder that contains subdirectories (e.g.
/Volumes/Pics/picz copy/ with year-subfolders 2024/, 2025/), no JPG or RAW
files are seen and the tool returns zero. index_folder is recursive, so the
tools disagree on which files exist.

Change:
Replace folder_path.iterdir() with folder_path.rglob("*") in both functions.
Keep the same extension filters. Add a recursive: bool = True parameter so
callers can opt out.

Acceptance:
Calling find_orphans on a folder whose RAW+JPG pairs live in subfolders
returns non-zero counts for both raw_orphans and jpg_orphans (or zero if
every file is paired).

P2 [CRITICAL] — score_image stores "" instead of None for eye sharpness on no-face photos
-----------------------------------------------------------------------------

Repo: triage-keepers
File: score_portraits.py
Function: score_image (lines 344 and 371)

Problem:
When no face is detected, or no eye crop is wide enough to score, the row
dict sets "eye_sharpness_min": "" and "eye_sharpness_max": "". These columns
are typed REAL in SQLite. Empty strings stored in REAL columns break
downstream consumers — MCP clients receive "" instead of null, and float(x)
raises if a callsite forgets to truth-check first.

Change:
Replace the two "" literals with None in the cv_scores dict on both branches
(no faces, and faces but no scoreable eyes). Update
tests/test_score_portraits.py::test_score_image_no_face to assert is None
instead of == "".

Acceptance:
score_image of a no-face fixture returns eye_sharpness_min is None; test
suite still passes; SQLite stores NULL for those rows.

Side effect:
Existing cached rows still have "". Either delete cache.db (under repo root,
~/Documents/coding/photography_code/triage-keepers/cache.db) or accept stale
"" until those photos re-index.

P3 [CRITICAL] — assess_subject_sharpness upserts a row with NULL mtime/size,
                 causing infinite re-scoring
-----------------------------------------------------------------------------

Repo: triage-keepers
File: server.py
Function: assess_subject_sharpness (line 189)

Problem:
On cache miss, the function calls score_image(...) then
_cache.upsert_photo(conn, row). But score_image does not set mtime or size —
those fields are populated by index_folder's batch loop. The cached row
therefore has mtime=NULL, size=NULL. The next call to _cache.needs_reindex(
conn, path, real_mtime, real_size) compares real values against NULL →
returns True → re-scores the same file on every call.

Change:
Before calling upsert_photo, stat the file and set
row["mtime"] = stat.st_mtime and row["size"] = stat.st_size. Also wrap the
upsert_photo call in `with _db_lock:` to match the locking convention used
by index_folder.

Acceptance:
Calling assess_subject_sharpness twice on the same un-indexed photo: first
call scores it, second call returns from cache (verified by short response
time or by adding a test that calls needs_reindex after the first
invocation and asserts False).

P4 [CRITICAL] — SQLite write race between assess_subject_sharpness and index_folder
-----------------------------------------------------------------------------

Repo: triage-keepers
File: server.py
Functions: assess_subject_sharpness (line 208), index_folder (line 174)

Problem:
index_folder holds _db_lock for its writes. assess_subject_sharpness does
not. If an MCP agent calls both concurrently (e.g. an indexing run plus a
thumbnail check), both threads can hit SQLite without coordination.
sqlite3.OperationalError: database is locked will be raised and there is
no retry path.

Change:
Wrap every _cache.upsert_photo(conn, ...) call in `with _db_lock:`. Audit
the file for any other upsert_photo callsites and apply the same pattern.
Optional: add a small retry helper that catches OperationalError, sleeps
0.1 * attempt, and retries up to 3 times.

Acceptance:
Grep for upsert_photo( in server.py — every call is inside a
`with _db_lock:` block.

P6 [MEDIUM] — find_burst_groups mega-clusters: hamming too loose, no time window
-----------------------------------------------------------------------------

Repo: triage-keepers
Files: server.py (line 304), cache.py (line 128)

Problem:
Default hamming=5 plus greedy transitive clustering means visually similar
backgrounds (e.g. outdoor portraits at the same location) chain into one
giant group. A 400-photo event becomes one group. The EXIF fix (commit
a360dec) now populates taken_at, so a time-window constraint is feasible.

Change:
1. In server.find_burst_groups, lower default hamming from 5 → 3.
2. Add parameter time_window_seconds: int = 60.
3. In cache.group_by_phash, accept an optional time_window_seconds. When
   set, two photos only group if their taken_at (parsed from
   "YYYY:MM:DD HH:MM:SS") is within the window AND their Hamming distance
   is within threshold.
4. Photos with missing taken_at should fall back to pHash-only grouping
   (don't drop them).

Acceptance:
On a 400-photo event folder, find_burst_groups(folder) returns multiple
small groups (typical 3–10 photos each) instead of one mega-group.

P8 [MEDIUM] — extract_exif swallows every exception silently
-----------------------------------------------------------------------------

Repo: triage-keepers
File: score_portraits.py
Function: extract_exif (line 190, except block at line 253)

Problem:
except Exception: pass hides EXIF parsing failures completely. If
get_ifd(0x8769) raises on a corrupt or unusual JPG, the caller sees a
fully-null EXIF dict with no clue why.

Change:
Replace the bare except Exception: pass with
except (OSError, KeyError, ValueError, TypeError, AttributeError) as e:
and log via
print(f"extract_exif failed for {path.name}: {e}", file=sys.stderr)
(or use logging.warning). Let unexpected exceptions propagate.

Acceptance:
A corrupted EXIF block in a test fixture produces a stderr log line and
returns None for the affected fields rather than silently failing.

portable with the photos. Option B is simpler and aligns with how the user
already inquired about per-folder storage.

This is a larger design change — write a short design note before
implementing.

P11.5 [MEDIUM] — Path-coupling: cached rows die when external drive remounts - Using option A from P11
-----------------------------------------------------------------------------

Repo: triage-keepers
Files: cache.py, server.py
Functions: init_db, get_photo, get_photos_in_folder, needs_reindex,
           index_folder, assess_subject_sharpness

Problem:
Cached paths are absolute. macOS remount as /Volumes/Pics SSD 1/
makes all 1,102 rows unreachable; system re-scores everything.

Change:
Implement relative-path storage with library_root:

1. Add library_root TEXT column to photos table (NOT NULL, indexed)
2. On index_folder(path, ...): set library_root = Path(path).resolve()
   Store relative paths: path.relative_to(library_root)
3. On queries (get_photo, get_photos_in_folder, needs_reindex):
   Accept optional library_root param; lookup by (relative_path, library_root)
4. On assess_subject_sharpness: infer library_root from photo path
5. Add migration script to convert existing absolute paths to relative
   (use Path prefix inference on first row)

Acceptance:
- Existing cache migrates without re-indexing
- index_folder("/Volumes/Pics SSD 1/...") finds rows from original /Volumes/Pics SSD
- get_photo(conn, "/Volumes/Pics SSD 1/2024/...", library_root) returns cached row
- needs_reindex detects matching (relative_path, library_root) and skips re-score
- Remount scenario: user re-runs index_folder on new mount path, zero re-scoring
